# Thread Statusbar

Плагин BB показывает метрики текущего или последнего хода Codex и Cursor в штатной строке контекста над полем ввода. Вдохновлён [CodexStatusbar](https://github.com/dongyue-19/codex-statusbar).

Провайдер и модель, состояние BB, длительность, средняя скорость, суммарные токены сессии, доля кеша и заполнение контекста. Пример с вымышленными данными:

```text
Codex · example-model · Готов · 00:10 · сред. 6 ток/с · Всего 1 160 ток · Кеш 40% · Контекст ≈300/1 000
```

Нажмите строку мышью либо выберите её Tab и нажмите Enter/Space: штатное раскрытие объясняет показатели. Поля переносятся в узкой панели и наследуют тему BB. Состояние принадлежит конкретному открытому треду; другие провайдеры, новый тред и редакторы сообщений не получают строку.

## Установка

Требуется BB **0.48 или новее** с Plugin SDK **0.6.94**. Используется экспериментальная поверхность `experimental_threadContextSegment`; совместимость с другой версией SDK требует проверки.

```sh
bb plugin install git:https://github.com/artbear/bb-plugin-thread-statusbar.git@main
```

После установки откройте существующий тред `codex` или `acp-cursor`. Настроек и собственных CLI-команд нет. События и контекст читаются публичным SDK BB; официальный output завершённого Codex turn дополнительно восстанавливается точечным чтением native rollout на машине выполнения: плагин не меняет треды, не читает auth-файлы и не отправляет метрики внешним сервисам.

## Как считаются показатели

- **Время:** от `turn/started` до текущего времени либо завершения того же основного хода. Включает инструменты и ожидания. Завершение, ошибка или прерывание замораживают время; новый ход сбрасывает его. Если начало или окончание неизвестно, показывается `—`.
- **Codex, сред. ток/с:** `(официальный cumulative output сейчас − достоверный output до начала хода) / полные секунды хода`. Например, 100 → 160 за 10 секунд дают 6 ток/с. Это средняя выдача за весь ход, не скорость декодирования. Output уже включает reasoning. Первый увиденный снимок не считается нулевым baseline. Изменившийся поздний usage прежнего хода делает baseline текущего неоднозначным: скорость скрывается.
- **Завершённый Codex без baseline:** собственный RPC `completedOutput({threadId, turnId})` проверяет основной закрытый ход по событиям BB, получает session/checkpoint и host из authoritative environment и вызывает единственный read-only host entry. Последний официальный `token_usage_record.turn_token_usage.output_tokens` того же завершённого native turn делится на те же полные секунды BB. Снимки заменяют друг друга; output уже включает reasoning. Это не `usage` последнего response и не session total.
- **Cursor, симв/с:** Unicode code points видимого ответа основного хода / полные секунды хода. `А🙂Б` за 2 секунды дают 1,5 симв/с. Завершённый снимок сообщения заменяет его дельты. Reasoning, stdout инструментов и вложенные/фоновые ходы исключены. Символы не переводятся в токены.
- **Всего:** `inputTokens + outputTokens` последнего корректного официального снимка сессии. Снимки не суммируются; кеш уже входит в input, reasoning уже входит в output. Валидный сессионный снимок позволяет показать всего/кеш даже без восстановленного начала хода; он сам по себе не доказывает baseline скорости.
- **Кеш:** `cachedInputTokens / inputTokens × 100%`. При нулевом input — `—`; настоящий нулевой cached input — `0%`.
- **Контекст:** независимое измерение провайдера `usedTokens / modelContextWindow`. `≈` сохраняет признак оценки; расход сессии не подставляется вместо контекста.
- **Модель:** записанное BB исполнение хода и подтверждённый fallback. Изменение picker для следующего сообщения не переименовывает текущий ход. `auto` не раскрывает фактическую backend-модель.

`—` означает отсутствие достоверного измерения. Cursor ACP может не отдавать token/cache/context: такие поля остаются неизвестными. Без подтверждённого baseline активного Codex хода скорость неизвестна. Завершённый ход допускает только проверенный native итог; при его отсутствии остаётся `—`. Отсутствие дельт не означает зависание. Время закрытого хода остаётся замороженным, а его поздний официальный usage или полный снимок текста может уточнить итоговую скорость. Некорректные и регрессирующие counters не сохраняют правдоподобную скорость.

Восстановление читает не более 2 000 последних подходящих событий страницами по 100. При пропущенном начале, baseline или неполном тексте зависимые метрики недоступны. События дедуплицируются по sequence. При ошибке чтения/разрыве связи цифры скрыты до успешной сверки; обновление приходит от штатных invalidation-событий. Незавершённое чтение отменяется через 15 секунд. Переподключение и переписанная история запускают повторную сверку. Счётчики и текст не сохраняются на диск плагином.

## Разработка и проверка

Нужны Node.js 22.15+ и установленный `bb` CLI 0.48. SDK закреплён exact devDependency: host использует только helpers, которые host builder встраивает в артефакт. BB предоставляет React и frontend SDK; runtime Zod находится в dependencies. Server регистрирует только собственный read-only RPC, без agent tools и CLI.

```sh
npm ci --cache /tmp/statusbar-npm-cache --ignore-scripts
npm run check
```

`check` запускает тесты, TypeScript и `bb plugin build`. Тесты проверяют trace → view, Unicode и reconciliation, baseline/reset, pagination, ошибки/reconnect, поздние ответы и cleanup; официальный SDK harness проверяет native registration, UI и публичность импортов. Сборка из чистой production-установки также проверена с `npm ci --omit=dev --omit=optional --ignore-scripts` и установленным BB CLI.

Для исходного выпуска проверены 38 тестов и живой BB 0.48.0: потоковые ответы обоих провайдеров, две split-панели, ширина 390 px, светлая/тёмная тема, клавиатурное раскрытие, reload и отключение/включение плагина. Независимые ревью стандартов, спецификации и интеграции завершены без открытых замечаний. См. [контракт](docs/specification.md), [план](docs/plan.md), [решения](docs/autonomous-decisions/thread-statusbar.md), [проверки](docs/validation.md), [ревью](docs/review.md) и [исследование](docs/research.md).

## Восстановление завершённых ходов в 0.1.1

Native JSONL — внутренний формат Codex, а не публичный history usage API BB. Host использует собственный `CODEX_HOME` (относительный путь разрешается от workspace подтверждённого environment), иначе `os.homedir()/.codex`. Если provider использует отдельный home, отсутствующий в окружении host worker, восстановление не гарантировано.

UUIDv7 session служит только локатором: перечисляются имена в `sessions/YYYY/MM/DD` за дату UUID ±1 сутки (граница локальной зоны), в `archived_sessions` и таких же датированных подпапках архива. Содержимое читается только при единственном совпадении точного имени session. Проверяются `session_meta.id`, `thread_id/session_id`, `turn_id/root_turn_id`, официальный cumulative output и последующий `task_complete` либо `turn_aborted` того же checkpoint. Синтетический BB turn id не используется как native id. Регрессия, неверные IDs, незавершённый/повреждённый файл и неоднозначность дают отсутствие данных.

Ограничения: 10 000 имён на каталог, 32 MiB на выбранный файл, 2 MiB на строку, 10 секунд host RPC и 15 секунд серверного запроса. Проверяются regular file, владелец ОС и отсутствие symlink в пути; изменение файла во время чтения отклоняется. Отмена закрывает файловый дескриптор. Повторного чтения на каждом UI tick или неизменившейся invalidation нет; результат живёт только в памяти открытого observer и связан с thread/session/turn/checkpoint/поколением. Ошибка native чтения затрагивает только неизвестную скорость, сохраняя доступные total/cache/context.

Приватность: разговоры разбираются только внутри host worker; он возвращает лишь проверенные UUID и число output, без текста, путей и сырых ошибок. Другие session contents, auth/config, SQLite и private provider RPC не читаются. Фонового collector, watch, кеша на диске или новых процессов Codex нет. Тестовые JSONL полностью вымышлены; live проверку выполняют отдельно от fixture тестов.
